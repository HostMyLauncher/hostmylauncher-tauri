# HostMyLauncher Tauri bridge

Optional Tauri 2 bridge between `hostmylauncher-rs` and launcher frontends.
The v1 implementation provides a Rust session service, an opt-in Tauri plugin and
a framework-independent TypeScript client. Validation status and remaining proof
are recorded in [IPC v1 tasks](odd/tasks/ipc-v1.md); this is not a published release.

## Packages

| Path | Package | Responsibility |
| --- | --- | --- |
| `crates/hostmylauncher-tauri` | `hostmylauncher-tauri` | Rust commands, IPC DTOs, structured errors, and operation events |
| `packages/tauri` | `@hostmylauncher/tauri` | Framework-independent TypeScript client and subscriptions |
| `examples/minimal-launcher` | Headless example | Real Rust service + built TS client with a local mock provider |

Cargo and pnpm manage their respective workspaces. No extra monorepo build system is required.

## Boundaries

- `hostmylauncher-rs` stays in its own repository and remains usable without Tauri.
- This bridge will depend on the base library; the base will not depend on this bridge.
- The Rust and TypeScript packages implement the two ends of one IPC contract.
- Launchers own orchestration across provider files, Minecraft, loaders, Java, accounts, and product state.
- Provider operation completion does not imply that a complete launcher installation is ready to play.
- The TypeScript package will not require React, Zustand, HeroUI, or another UI framework.
- Downstream launcher applications remain external consumers rather than members of this repository.

## Contract and versions

The approved v1 design is documented in [IPC contract v1](docs/ipc-v1.md).
Implementation and verification are tracked in [IPC v1 tasks](odd/tasks/ipc-v1.md).
Detailed verification progress, typed integrity errors and cancellation/interruption
are deferred to v2, after the base library's public API supports them.

Rust IPC DTOs are the source of truth for TypeScript transport types generated by
`ts-rs`. A shared Rust registration macro supplies command identifiers to the
plugin handler, permission metadata and TypeScript generator. The event identifier
is also generated. Generated files must not be edited by hand.

Both bridge packages start at `0.1.0` and are intended to be released as a compatible pair.
The base library keeps its independent versioning. Dependency ranges will be chosen during integration.

Publishing is disabled for both packages. No license is selected yet; choose one before publication.

## Development checks

The Rust dependency currently points to the sibling checkout `../hostmylauncher-rs`;
this is a development configuration, not reproducible published dependency sourcing.
Enable the Rust `plugin` feature in a consuming Tauri application. Host setup and
capabilities are documented in [Rust development](crates/hostmylauncher-tauri/DEVELOPMENT.md).

Use Node 22+ and pnpm. Dependency installation and initial Cargo builds may require
network access and take longer than later checks. Keep temporary fixtures off tmpfs:

```sh
mkdir -p target/test-tmp
export TMPDIR="$PWD/target/test-tmp"
pnpm install
cargo fmt -p hostmylauncher-tauri -- --check
cargo test --workspace
cargo run -p hostmylauncher-tauri --bin generate-contract -- --check
cargo check -p hostmylauncher-tauri --features plugin
cargo test -p hostmylauncher-tauri --features plugin-tests --test plugin_ipc
pnpm typecheck
pnpm test
pnpm build
```

To regenerate the checked-in contract after changing Rust DTOs or identifiers:

```sh
cargo run -p hostmylauncher-tauri --bin generate-contract
```

See the [minimal consumer](examples/minimal-launcher/README.md) for its build/smoke
commands and the [capability host](examples/capability-host/README.md) for the actual
consuming-app permission-discovery build check. Headless service and MockRuntime IPC tests are not real WebView proof.
Format only the bridge package: `cargo fmt --all` also traverses local path
dependencies and must not be used here because the sibling base is read-only.
Scoped fixtures clean up normally; inspect only `target/test-tmp` after interrupted
checks. Cargo build outputs and generated distribution files are intentional outputs.

## Future task: CI divergence checks

Status: pending. No CI workflow is implemented yet. Wire the local package,
generation and minimal-example checks into CI after their implementation is validated.

Every change must pass:

- [ ] Rust bridge compilation and tests.
- [ ] Transport-type regeneration with no pending differences in generated files.
- [ ] TypeScript client typecheck and tests.
- [ ] Command and event name correspondence between the Rust bridge and TypeScript
      client, not just compatibility of their payloads.
- [ ] Integration of both packages in the minimal launcher example.

Matching payload types alone is insufficient: the client could still invoke a
command that the Rust bridge does not expose, or subscribe to a mismatched event name.
Keep this task open until all five checks are enforced by CI.
